PRD · Minimal Visitor Flow MVP

Visitor Flow Requirements

Goal: enable the visitor lifecycle from scheduling to completion Scope: host, visitor, reception/security
This PRD focuses only on the pages required to make the visitor journey work end to end without expanding into the full admin system.

1. Objective

Build the smallest set of pages needed to support the visitor journey shown in the flow: Host creates appointment → invitation issued → confirmation → approval → arrival check-in → active visit → sign-out/completion.

This is not a full visitor management suite. It is the minimal path required to make the workflow usable and believable.

2. In Scope

  • Host creates appointment
  • Visitor invitation and confirmation
  • Visitor check-in page
  • Security / reception dashboard
  • Visit summary / completion page

3. Out of Scope

  • Full admin panel
  • Bulk visitor import
  • Advanced reporting
  • Deep role management beyond basic host, visitor, and security
  • Full notification engine beyond status updates
  • Multi-tenant configuration

4. Core User Flows

Flow A: Host schedules a visit

  • Host opens the appointment page
  • Enters visitor information, date, time, purpose, and notes
  • Saves the appointment
  • System creates a visit in Pending status
  • System generates an invitation link or confirmation prompt

Flow B: Visitor confirms the visit

  • Visitor opens the invitation link
  • Sees host, date, time, purpose, and location
  • Confirms or declines
  • System updates status to Confirmed or Rejected

Flow C: Visitor arrives on site

  • Visitor goes to check-in
  • Reception or security verifies identity
  • System marks the visitor as Checked In
  • Visit becomes active and tracked

Flow D: Visit ends

  • Visitor exits the premises
  • Security or reception records sign-out
  • System marks the visit as Completed or Signed Off
  • Visit becomes historical and read-only

Alternate branch

  • Visitor ignores or declines the invitation
  • Host or security rejects the request
  • Visit ends with Rejected status

5. Required Pages

Page 1: Host appointment creation

Purpose: Create the initial visit request.

Fields: visitor name, email, phone, host, visit date, time, purpose, notes, location.

Actions: Create appointment, save draft, cancel.

Behavior: new entries default to Pending, validation is required, and a confirmation is shown after save.

Page 2: Visitor invitation / confirmation

Purpose: Let the visitor confirm or decline the scheduled visit.

Content: host, date, time, purpose, location, confirmation and decline actions.

Behavior: confirmed moves to Confirmed, declined moves to Rejected, no action keeps the record in Pending.

Page 3: Visitor check-in

Purpose: Allow on-site check-in.

Content: visitor details, scheduled visit information, identity verification, and optional notes.

Actions: Check in, cancel.

Behavior: only confirmed or approved visits can be checked in; on success the status changes to Checked In.

Page 4: Security / reception dashboard

Purpose: Operational overview and actions for staff.

Sections: Pending, Confirmed, Checked In, Completed, Rejected.

Actions: approve, reject, check in, check out, view details.

Page 5: Visit summary / completion

Purpose: Close the visit and show final outcome.

Content: visitor, host, time window, status history, check-in/out timestamps, notes.

Actions: mark complete, view details, return to dashboard.

6. Functional Requirements

  • Every visit must have a single lifecycle status.
  • Status transitions must be clear and chronological.
  • Each page must reflect the current state of the visit.
  • Impossible transitions must be blocked by validation.

Status model

PendingRequest created but not yet actioned
ConfirmedVisitor has accepted the invitation
Checked InVisitor has arrived and is active on site
CompletedVisit has ended and was signed out
RejectedRequest was declined or denied

7. Acceptance Criteria

  • A host can create a visit with required fields.
  • The record is stored with Pending status.
  • A visitor can confirm or decline the request.
  • The system updates the status correctly.
  • A confirmed visitor can be checked in.
  • A checked-in visitor can be signed out and marked complete.
  • Reception can view all visits by status and act on them without unrelated admin navigation.

8. MVP Success Metrics

  • Host can create an appointment in under two minutes.
  • Visitor can confirm in under one minute.
  • Staff can check in a visitor in under 30 seconds.
  • Most visitor flows complete without hitting a dead end.

9. Risks and Open Questions

  • Should Confirmed and Approved be the same state or separate states?
  • Should sign-out happen automatically or be a manual staff action?
  • Will invitations be delivered via email, link, or QR?
  • Should the reception dashboard be a dedicated page or part of a broader host dashboard?

10. Recommended MVP Implementation

Keep the first build focused on the visitor lifecycle only. The best minimal page set is:

  1. Host appointment page
  2. Visitor confirmation page
  3. Reception check-in page
  4. Visit summary / completion page

If needed, add a fifth page for the security dashboard overview later, but do not broaden the initial scope beyond the lifecycle itself.
